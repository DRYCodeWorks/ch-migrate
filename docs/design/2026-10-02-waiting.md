# Waiting for mutations and distributed DDL

**DRY-1398 · 2026-10-02 · Recovery policy approved by Dan on 2026-10-04.**

A write-ahead intent plus a marker carried into ClickHouse's mutation record can
recover an accepted `UPDATE` after the client dies without reading its response.
The experiment passes three times: the resumed process observes the same mutation
ID, waits, and the counter ends at 1, not 2.

That is **not an unconditional replay guarantee**. Completed mutation records can
expire while the client is dead. An intent without a surviving marker cannot tell
us whether the request never arrived, is still being submitted, or completed and
was removed from the system table. Reissuing can apply `x = x + 1` twice; skipping
can omit it. No command-normalization or time-window heuristic fixes that.

**Approved recovery rule:** when an interrupted statement's outcome cannot be
proven, exit nonzero, do not reissue it, do not mark the migration complete, and
require operator reconciliation. Known unfinished work still reattaches
automatically. Dan approved this exception to
[capabilities 4 and 5](2026-10-02-ch-migrate-1.0.md) and explicitly resumed
local-only implementation on 2026-10-04.

Approval revalidation on 2026-10-04: all 16 local experiments passed; the separate
three-trial kill/re-run pass passed. The local CI gate passed 641 tests on each of
Python 3.10, 3.11, 3.12, 3.13 and 3.14. The implementation rows below remain the
acceptance contract for DRY-1399/1400, not claims that those features already exist.

## Q5. Recognize our work without claiming another writer's work

### What the server preserves

The metadata probe queries `system.columns` and submits these two requests with
distinct `query_id` and `log_comment` settings:

```sql
ALTER TABLE db.ownership UPDATE x = x + 1
WHERE id = 1 /* chm_marker_comment */;
ALTER TABLE db.ownership UPDATE x = x + 1
WHERE id = 2 AND 'chm_marker_expression' = 'chm_marker_expression';
SELECT mutation_id, command, is_done
FROM system.mutations WHERE database = 'db' AND table = 'ownership';
```

Observed with merges stopped:

```text
mutation_2.txt | (UPDATE x = x + 1 WHERE id = 1) | 0
mutation_3.txt | (UPDATE x = x + 1 WHERE (id = 2) AND
                  ('chm_marker_expression' = 'chm_marker_expression')) | 0
```

`system.mutations` has `mutation_id` and `command`, but no query ID or log comment.
The comment disappears. The literal expression survives. `system.query_log`
preserves query IDs and log comments, but the experiment's mutation-related
`ProfileEvents` map is empty: it supplies no query-to-mutation receipt. Query logs
are also asynchronously flushed and retained for a bounded period.

**Rejected identities:** normalized SQL, table plus timestamp, and before/after ID
set difference. Another writer can issue the same statement in the same window.
Those techniques can identify candidates or preceding blockers, not ownership.
`formatQuery()` would normalize spelling, not make a command unique.

### A durable marker within the submitted operation

For an `ALTER UPDATE`, a combined empty delete preserves the original predicate
and adds a unique marker:

```sql
ALTER TABLE db.counter
  UPDATE x = x + 1 WHERE 1,
  DELETE WHERE 0 AND 'chm_step_TOKEN' = 'chm_step_TOKEN'
SETTINGS mutations_sync = 0, alter_sync = 0;
```

Observed: two command rows, **one mutation ID**. Counting rows in
`system.mutations` is not counting distinct mutations.

```text
mutation_2.txt | (UPDATE x = x + 1 WHERE 1) | 0
mutation_2.txt | (DELETE WHERE 0 AND ('chm_step_TOKEN' = 'chm_step_TOKEN')) | 0
```

The three killed-client trials each printed:

```text
resumed mutation_2.txt; mutation_ids=['mutation_2.txt']; command_rows=2; x=1
```

The original and final sets of mutation IDs were equal. The resumer remained
running while merges were stopped and completed after `SYSTEM START MERGES`.

For schema changes, **do not assume the marker shares the mutation ID**:

| Combined `ALTER` action | Observed command IDs |
|---|---|
| `MODIFY COLUMN x UInt32, DELETE WHERE <empty marker>` | schema `mutation_2.txt`, marker `mutation_3.txt` |
| `MATERIALIZE COLUMN y, DELETE WHERE <empty marker>` | both `mutation_2.txt` |
| `CLEAR COLUMN y, DELETE WHERE <empty marker>` | schema `mutation_2.txt`, marker `mutation_3.txt` |
| `RENAME COLUMN y TO renamed, DELETE WHERE <empty marker>` | schema `mutation_2.txt`, marker `mutation_3.txt` |

Thus a marker is a **completion barrier**, not necessarily the original mutation.
Wait for its command rows and all preceding outstanding work on that table; never
infer the original command's completion from a different table's marker. Inspect
failures in preceding mutations rather than reporting only the empty delete.
Persist the table UUID so that dropping and recreating a name cannot make an old
intent apply to a different table.

The empty-marker cost probe used 10,000 rows with a payload column. It retained all
10,000 rows. `system.part_log` reported a `MutatePart` event with `read_rows = 0`,
`read_bytes = 0`, and `MutationUntouchedParts = 1`, but also file reads and buffer
allocations in `ProfileEvents`. The marker is not free. It also requires DELETE
privilege. Predicate markers avoid that extra command for suitable UPDATE/DELETE
statements, but require syntax-aware insertion and their own corpus proof.

### Minimal runtime state

One append-only server-side journal, deployed with the same replication policy as
the version table, stores:

- revision and statement position;
- exact statement/parameter digest, target database/table and UUID;
- unique attempt token and operation kind;
- phase: intent, accepted receipt, completed;
- receipt: mutation marker/IDs or DDL queue entry, plus required hosts.

Write and acknowledge intent **before** sending SQL. Never derive the intent only
after submission. Record completion before moving to the next statement. An
unfinished revision reuses its attempt, validates its digest and target UUID,
skips completed work, and attaches to known unfinished work. A changed migration
or replaced target fails before submission. Successful downgrade must invalidate
that revision's old completed journal, so a subsequent upgrade actually runs.

The insertion-deduplication probes establish only a useful primitive, not a lock:
with a stable `insert_deduplication_token`, two single-node inserts retained the
first owner; concurrent replicated inserts through both nodes retained the same
one owner on both. Deduplication has a retention window. Do not turn this result
into an unbounded exactly-once or concurrent-run claim. Concurrent migrators need
serialization; this spike has not proved a portable fencing lock.

### Missing-evidence recovery

If the process dies after preparing intent but before receiving a durable receipt,
look up the marker. If it is present, attach without submitting again. If it is
absent, **absence is not completion and is not permission to retry**.

There are at least three indistinguishable histories at this boundary:

1. Intent was committed; SQL never reached the server.
2. SQL reached the server but has not registered its marker yet.
3. SQL completed; the process died before recording completion; the server later
   removed the completed marker under its retention policy.

The retention probe sets `finished_mutations_to_keep = 1`, `old_parts_lifetime = 0`,
`cleanup_delay_period = 1` and `cleanup_delay_period_random_add = 0` on its disposable
table, completes a marked increment and then another mutation. Observed:
only `mutation_3.txt (DELETE WHERE 0)` remains, while the counter is still 1.
The first trial without accelerated cleanup retained both records for 30 seconds;
retention is asynchronous, not immediate after the next mutation.
A resumed journal reader has no receipt to distinguish
that history from an unsubmitted operation. Unfinished records surviving a
normal mid-wait SIGKILL do not establish that completed records survive forever.

**Approved exception:** fail with `outcome unknown; statement not reissued;
migration incomplete`, including the intent token, revision, statement position,
target UUID, and read-only diagnostic queries. The operator must stop concurrent
runners, establish the actual outcome from independent evidence, and reconcile
the data and that specific journal record in a reviewed manual operation before
resuming. An absent server record alone never authorizes replay or completion.
There is no automatic stamp, retry override, blind journal deletion, or KILL.

## Q6. Foreign mutations ahead of ours

The probe submits a failing foreign mutation, then a second update:

```sql
ALTER TABLE db.foreign_probe UPDATE x = throwIf(x = 5) WHERE 1;
ALTER TABLE db.foreign_probe UPDATE x = x + 1 WHERE id = 1;
```

Observed:

```text
mutation_2.txt | is_done=0 | parts_to_do=1 | Code: 395 ... throwIf ...
mutation_3.txt | is_done=0 | parts_to_do=1 | latest_fail_reason=''
rows: [(1, 1), (5, 5)]
```

Recommendation: before creating more work on that table, report and wait for
healthy preceding foreign mutations. A preceding failure exits nonzero with its
host, reason and exact operator-only `KILL MUTATION` command. Do not label it as
our mutation or insert another mutation behind a known permanent failure. A
foreign mutation arriving after our completion barrier is not a reason to hold
our revision open. An operator's KILL is not proof our work succeeded.

## Q7. Every replica, not merely the connected replica

The cluster probe creates a ReplicatedMergeTree, inserts a row, and synchronizes
node 2. It stops merges, fetches and replication queues **on node 2 only**, submits
an increment through node 1, then pulls the mutation metadata on node 2.

```text
node 1: mutation_id=0000000000, is_done=1, parts_to_do=0
node 2: mutation_id=0000000000, is_done=0, parts_to_do=1
```

After restarting those operations and synchronizing node 2, its counter is 1.
A local-only query would have reported success too early.

Rules for self-hosted replicas:

- Snapshot the required topology before submission. Use the configured cluster or
  a Replicated database's generated cluster, and verify coverage against the
  table's replica metadata. Missing topology is an error, not permission to wait
  only locally.
- Query every required host's `system.mutations`, for example with
  `clusterAllReplicas`. Identify hosts as well as mutation IDs; IDs are not global
  across unrelated tables/shards.
- Require `is_done = 1` for every command row of every required mutation on every
  required replica. `parts_to_do = 0` is progress, not completion: a long insert
  may still add a part that must be mutated.
- A host omitted by `skip_unavailable_shards` is missing evidence, not success.
  Track required hosts separately. A missing record is likewise not a completed
  record unless the journal already stores that host's completion.
- Persist observed completion so later retention cannot erase an already-proved
  result. The crash before persisting that result remains Q5's blocker.

## Q8. Distributed DDL and a down host

The probe stops node 2 and submits:

```sql
CREATE TABLE db.ddl_owned ON CLUSTER it_cluster (id UInt64) ENGINE = Memory
SETTINGS distributed_ddl_task_timeout = 0,
         distributed_ddl_output_mode = 'none', log_comment = 'chm_ddl_TOKEN';
SELECT entry, host, settings['log_comment'], status
FROM system.distributed_ddl_queue
WHERE settings['log_comment'] = 'chm_ddl_TOKEN';
```

Observed one entry, `query-0000000001`, with both target hosts and the same marker:
node 1 `Active`, node 2 `Inactive`. ClickHouse inserted a UUID into the stored CREATE
query. Exact comparison with the original SQL would not identify it reliably.
The `settings['log_comment']` marker survived and is a better identity.

Rules:

- Write intent first. Set a unique, journaled `log_comment` for the request. Preserve
  any caller comment in the journal rather than treating it as the identity.
- Submit with `distributed_ddl_task_timeout = 0` and output mode `none`, then poll
  the queue by marker/entry. The server's synchronous client timeout is not the
  migration's completion test.
- Success requires every recorded target host to be `Finished` with
  `exception_code = 0`. `Finished` alone can mean failure. Missing rows,
  `Inactive`, `Active`, `Removing` and `Unknown` are not success.
- A down host stays pending. Default wait has no deadline; `--timeout` exits
  nonzero naming the host, queue entry and status. It does not delete queue work.
  Once the host returns, rerun attaches to the same entry.
- Any nonzero exception exits nonzero with host, code and text. The failure probe
  pre-adds `conflict String` only on node 2, then enqueues `ADD COLUMN conflict
  UInt64` on both. This produces a host-specific schema error without a network
  timeout or an intentionally stuck mutation.
  Observed queue results: node 1 `Finished / 0`, node 2 `Finished / 15`
  with `Cannot add column conflict: column with this name already exists`.
- For mutation-producing `ALTER ... ON CLUSTER`, finish both barriers: all hosts
  executed DDL **and** all required mutations finished. Neither subsumes the other.
- Queue retention creates the same unknown-outcome boundary as Q5. A missing
  entry must not trigger blind DDL resubmission.

## Q9. Cloud: reasoned, not tested

DRY-1413 has no `service ready` comment. No Cloud connection or credential lookup
was made for this note. These conclusions come from official documentation, not
the local replicated harness:

- The [system.mutations documentation](https://clickhouse.com/docs/reference/system-tables/mutations)
  says each Cloud node exposes all cluster mutations, so `clusterAllReplicas` is
  unnecessary for this table.
- The [SharedMergeTree reference](https://clickhouse.com/docs/products/cloud/features/infrastructure/shared-merge-tree)
  describes shared mutation work, not a per-replica rewrite. It also states that
  `system.replication_queue` is not the SharedMergeTree introspection API.
- Cloud converts MergeTree-family tables to SharedMergeTree-family tables. The
  journal should follow that policy, not introduce a self-hosted Keeper path.
- `ON CLUSTER` is unnecessary on Cloud. Skip the distributed-DDL mechanism for
  ordinary Cloud DDL; do not invent a cluster or infer completion from a
  self-hosted replica queue.

The 0.7 acceptance ticket must prove mutation visibility, marker preservation,
retention behavior, session continuity and journal persistence on the authorized
Cloud service. Local success cannot close these checks.

## Which statements create mutation records

The corpus experiment runs each statement on a fresh seeded MergeTree table and
queries `system.mutations` afterward. It leaves completed records in place for
inspection.

| Statement | Observed record on 26.3.39.7 |
|---|---|
| `ALTER ... UPDATE` | `UPDATE ...` |
| `ALTER ... DELETE` | `DELETE ...` |
| lightweight `DELETE FROM` | `UPDATE _row_exists = 0 ...` |
| lightweight `UPDATE ... SET` | no mutation record; patch data already visible |
| `MODIFY COLUMN x UInt32` | `MODIFY COLUMN x UInt32` |
| `DROP COLUMN y` | `DROP COLUMN y` |
| `CLEAR COLUMN y` | `CLEAR COLUMN y` |
| `MATERIALIZE COLUMN y` | `MATERIALIZE COLUMN y` |
| `RENAME COLUMN y TO z` | `RENAME COLUMN y TO z` |
| `MODIFY TTL ts + INTERVAL 1 DAY` | `MATERIALIZE TTL` |
| `UPDATE x = throwIf(x = 5)` | pending record with failure code 395 |

The first lightweight UPDATE attempt failed with code 48 because the required
storage columns were disabled. With `enable_block_number_column = 1`,
`enable_block_offset_column = 1`, and `allow_experimental_lightweight_update = 1`,
it returned rows `[(1, 11), (2, 20)]` and **no** `system.mutations` rows. It must not
be modeled as a background mutation that is complete merely because a lookup is
empty. Wait for its synchronous request; patch-merge completion is not a mutation
completion signal. Do not silently rewrite it as a heavyweight UPDATE.

`MODIFY TTL` can produce work under a different command string. Generic command
matching would miss it. The implementation corpus must cover query/session
settings that change materialization, including `materialize_ttl_after_modify`.

## Execution, sessions, version state and output

### Hook at the actual cursor boundary

Use SQLAlchemy `before_cursor_execute` with `retval=True` and
`after_cursor_execute` on the migration connection, as established by DRY-1391.
This covers `op.execute`, `op.get_bind()` and `run_sql`'s `exec_driver_sql` path.
Do not use only `ChMigrateImpl._exec`. Guard journal, polling and progress queries
against recursive instrumentation. Offline SQL generation does not connect or
invent journal receipts.

Poll on the same migration session, using bounded requests and an interval less
than its idle timeout. This both preserves session `SET`s and keeps the session
alive. Propagate DRY-1392's expired-session failure; never silently recreate it.
A separate monitoring client alone does not keep the migration session alive.

Online `up` invokes Alembic in the CLI process, so SIGKILL cannot leave a child
Alembic runner advancing the version after its parent dies. A narrow revision-step
adapter establishes the journal scope; cursor events still cover every SQL path.
Pre-hooks share the resumable batch scope. Post-hooks run after the revision body
but before its version transition, so their mutations are covered by the same
completion barrier.

### Do not hold a request open to wait

The managed request uses asynchronous mutation settings and polls afterward.
The settings probe submits a stopped mutation with both `mutations_sync = 2` and
then `mutations_sync = 0`; it returns while both command rows remain unfinished.
That proves the last duplicate value wins on this server, not that text appending
is a general SQL-rewriting strategy. Parse and replace managed settings instead
of relying on duplicate-setting precedence. Do not permanently reset unrelated
session settings.

`MODIFY TTL` cannot take an appended ALTER marker: its comma-separated TTL-rule
grammar consumes the apparent next action. The runtime therefore acknowledges
the metadata change with automatic materialization disabled, journals that
boundary, and submits `MATERIALIZE TTL` with its own marker. A resume does not
repeat either submitted operation. Existing session/per-query opt-out is honored.
An unacknowledged metadata change remains an unknown outcome under the approved
rule; it is not silently reissued. Executemany writes re-enter the single-statement
path for each parameter set, preserving an independent intent and completion
barrier rather than collapsing intermediate TTL effects into one materialization.

The journal and version INSERTs explicitly disable asynchronous insertion. A
migration's session `async_insert=1, wait_for_async_insert=0` must not turn control
state into queued, unacknowledged data.

### The version table's delete

DRY-1412 inserts the new head before deleting the previous one. Its delete is a
real mutation and currently uses the official implementation's synchronous wait.
The waiting implementation must put that delete through the same asynchronous
polling/error surface, without weakening the insert-first safety invariant.
After interruption, both heads may be present; that is a fail-closed overlap, not
permission to replay the revision. Attach to the known version-delete receipt
before evaluating the next revision. Never emit “applied” until the delete barrier
finishes. This is not a promise of transactional rollback of the inserted head.

### Progress and exits

Stable message semantics (data substituted, not literal output fixtures):

- Progress: `Waiting: db.table mutation ID host HOST; N parts; Ns elapsed`.
- Failure, exit 1: `Mutation failed: ... REASON`, followed by an operator-only
  `KILL MUTATION WHERE database = 'db' AND table = 'table' AND mutation_id = 'ID'`.
  On clusters, name the affected host; do not suggest an unscoped kill.
- Timeout, exit 1: `Timed out; server work continues; revision not completed`,
  followed by every pending mutation/host/DDL entry and its last known state.
- Foreign failure, exit 1: `Blocked by foreign mutation ...`, reason and command.
- Unknown outcome, exit 1: `Outcome unknown; statement not reissued;
  migration incomplete`, intent token, target UUID and reconciliation requirement.
- Configuration/permission/topology error: exit 1 with the actual error; never a
  zero-work success. Existing CLI usage errors remain Click's exit 2.

Use a live line only on a TTY. In CI, emit an initial plain line, state changes,
periodic summaries, and a final result to stderr. Use monotonic elapsed time and
one optional `--timeout SECONDS` budget for the invocation's waits, not a fresh
budget for each host. No default timeout; no automatic mutation/DDL cancellation.

  command rows, IDs, completion versus parts, Cloud visibility.

  settings, per-host status and exception columns.
- [SharedMergeTree](https://clickhouse.com/docs/products/cloud/features/infrastructure/shared-merge-tree):
  shared mutation work and metadata visibility.
- Local SQL/output: `tests/integration/waiting_spike_probe.py` and the two scripts
  linked above. These probes are not the `up` implementation and do not imply that
  its acceptance tests pass yet.

This note does not authorize Cloud use or release a version. Its approved
unknown-outcome rule does not claim an unbounded exactly-once protocol from
bounded server records.
