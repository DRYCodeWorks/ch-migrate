# ch-migrate 1.0 — product definition

**Status:** Accepted · 2026-10-02
**Scope:** what ch-migrate 1.0 is, what it is not, and what each release delivers. Task-level
planning lives in the project's tickets, one milestone per version.

## The problem

Migrating a ClickHouse schema in production goes wrong in ways a Postgres-trained migration tool
never anticipates. We have hit every one of these on production systems:

- **An `ALTER` that returns is not an `ALTER` that finished.** Column type changes,
  `MATERIALIZE`, `UPDATE` and `DELETE` start a mutation that rewrites parts in the background.
  The migration is recorded as applied while the rewrite is still running, and it can still fail.
- **Some changes cannot be made in place.** A different sorting key or engine means building a
  new table and swapping it in. Rows written during that window are easy to lose.
- **Materialized views are insert triggers.** Changing a table underneath one can break inserts
  into the source table, not just the view.
- **There are no transactions.** A migration that fails halfway leaves the schema somewhere
  between two revisions, and the version table does not say where.
- **Some statements are silently ignored.** Over the HTTP interface without a session, a
  standalone `SET` applies to nothing.

## Where ch-migrate sits

As of clickhouse-connect 1.9, ClickHouse maintains an official Alembic integration
(`clickhouse-connect[alembic]`): a dialect, autogenerate for tables and columns, and operations
for skipping indexes, projections, materialized views and dictionaries. That integration turns
Alembic operations into ClickHouse DDL.

**ch-migrate does not compete with it. ch-migrate is the layer that knows what that DDL will do
to a live cluster, and runs it safely.** Concretely:

| Concern | Owned by |
|---|---|
| SQLAlchemy dialect, DDL compilation, autogenerate | clickhouse-connect (official) |
| Revision graph, `upgrade` / `downgrade` mechanics | Alembic |
| SQL-first authoring: migrations written as SQL files, not Python | **ch-migrate** |
| Environments, credentials, bootstrap of databases, roles and users | **ch-migrate** |
| Static and live analysis of pending migrations (`lint`, `deps`, `plan`) | **ch-migrate** |
| Re-runnable migrations: idempotency enforced before anything runs | **ch-migrate** |
| Waiting on mutations and distributed DDL before declaring success | **ch-migrate** |
| Table rebuilds (shadow table + `EXCHANGE TABLES`) | **ch-migrate** |
| Drift detection between the migration head and the live schema | **ch-migrate** |

Other tools in this space take different positions: golang-migrate, goose and dbmate run SQL
files in order; Atlas is declarative schema-as-code. ch-migrate is SQL-first like the first group,
and adds the ClickHouse-specific operational safety none of them attempt.

## Who it is for

Teams running ClickHouse in more than one environment (ClickHouse Cloud or self-hosted), whose
migrations run from CI or by an operator, and who have been bitten — or expect to be — by one of
the problems above. Migrations are written in SQL. You need Python installed to run the CLI, not
a Python codebase.

## What 1.0 is

Capabilities are listed in release order. Each has an acceptance check that can be observed, not
asserted.

### 1. One name, installable from PyPI

- `pip install clickhouse-alembic` / `uv tool install clickhouse-alembic` installs the CLI
  `ch-migrate`. (PyPI rejects `ch-migrate` as too similar to an existing project, `chmigrate`.)
- The import package stays `clickhouse_alembic`, so existing migration files
  (`from clickhouse_alembic import get_db, read_sql`) keep working unchanged.
- `ch-migrate --version` reports the released version.
- CI runs the test suite on every supported Python version on every push (see Compatibility).
  Pushing a `vX.Y.Z` tag publishes that version through PyPI Trusted Publishing and creates the
  GitHub release.

**Accept:** a clean virtualenv installs from PyPI, `ch-migrate --version` matches the tag, and
the existing test suite passes in public CI.

### 2. SQL-first migrations

- A migration is an upgrade SQL file and a downgrade SQL file. `ch-migrate new` creates both,
  in the existing object-centric SQL history layout, along with the Alembic revision that runs
  them. A schema change needs no Python.
- A SQL file may hold several statements. ch-migrate splits it and runs one statement per
  request, because the ClickHouse HTTP interface accepts one statement at a time. `{db}`
  substitution works as it does today.
- Python stays available for migrations that need logic, such as reading a value or branching;
  `read_sql` and `get_db` remain the API for those.
- A migration can be declared irreversible. `down` then refuses with a clear message instead of
  running a downgrade that cannot restore the data (a dropped column comes back empty).

**Accept:** `ch-migrate new dev add_status --table logs` produces upgrade and downgrade SQL files
and a revision that applies them with no Python edits; a SQL file with two statements applies
both; the README quick start contains no Python.

### 3. Session-safe connections on the official dialect

- The requirement: a session-scoped `SET` in one statement applies to the statements after it
  in the same migration, and the generated `env.py` holds one session for the whole migration.
- ch-migrate moves to the official clickhouse-connect dialect and its Alembic integration,
  which holds a session per connection
  ([dialect spike](2026-10-02-dialect-spike.md)). A session that expires while idle must fail
  loudly, not quietly drop its settings.
- The version table cannot cause a migration to run twice. The version advances by inserting
  the new row and then deleting the old one, waiting for the delete. An interrupted run is
  therefore refused, not repeated. Today's `ALTER … UPDATE` returns before it is applied, and
  the spike reproduced a migration running twice because of it.
- The version table is created to suit the deployment: shared on ClickHouse Cloud, replicated in
  a replicated database or on a configured cluster, plain on a single server.
- `ch-migrate upgrade-env` moves an existing project to the new `env.py`. Existing version tables
  keep working.
- `ch-migrate lint` rejects a standalone `SET` on a transport where it would be ignored.

**Accept:** an integration test against a real ClickHouse server shows a `SET` in one
statement taking effect in the next; an existing 0.x project upgrades with `upgrade-env` and
runs `up` without editing migration files; with the version table's delete held back, a second
`up` refuses instead of re-running a migration.

### 4. Re-runnable migrations

ClickHouse cannot roll a migration back, so ch-migrate guarantees the next best thing: any
migration can be run again after a partial failure and reach the same schema as a clean run.

- `lint` treats a statement that is not idempotent as an **error**, not a warning: `CREATE`
  without `IF NOT EXISTS`, `DROP` without `IF EXISTS`, and `ALTER … ADD/DROP` of columns,
  indexes and projections without the matching `IF` clause; `CREATE USER` / `ROLE` without
  `IF NOT EXISTS`.
- Statements that cannot be made idempotent by syntax (`EXCHANGE TABLES`, `INSERT … SELECT`,
  `RENAME`, `UPDATE` / `DELETE` mutations) need either a per-statement waiver with a written
  reason, which shows up in review, or `op.rebuild_table()`, which guards its own steps.
- There is no command-line flag to skip the gate. A waiver in the migration file is the only way
  past it, so every exception is visible in review and in git history.
- `up` runs the static lint before applying anything and refuses a migration that fails it.
  Only the idempotency rules and the standalone-`SET` rule block `up`; every other lint finding
  (destructive changes, reserved words, `ON CLUSTER`, materialized-view dependencies) stays a
  warning.
- The documented recovery from a partial failure is: fix the cause, run `up` again.

**Accept:** a fixed corpus of statements is classified correctly; `up` refuses a migration with
an unwaived non-idempotent statement; an integration test stops a migration halfway, runs `up`
again, and reaches the same schema as a clean run.

### 5. Migrations that wait for the work they start

`up` does not record a migration as applied until ClickHouse has finished the work the migration
started.

- After each statement that creates a mutation, `up` polls `system.mutations` until the mutation
  finishes, showing progress. It does not rely on `mutations_sync`, which holds one HTTP request
  open for the whole rewrite and loses the outcome if the connection drops.
- For `ON CLUSTER` DDL, `up` waits on the distributed DDL queue rather than trusting the
  client-side timeout.
- Waiting is on by default. There is no default timeout; `--timeout` sets one.
- Whenever `up` stops waiting (a timeout, a killed CI job, a dropped connection), the outcome is
  the same: the migration is not recorded as applied, ClickHouse keeps doing the work, and the
  next `up` finds the unfinished mutation and waits on it instead of issuing the statement again.
  Issuing `UPDATE … SET n = n + 1` twice applies it twice.
- A failing mutation does not end on its own: ClickHouse retries it and holds back every later
  mutation on the same table. `up` reads `latest_fail_reason`, fails the migration, and prints the
  `KILL MUTATION` statement for the operator. ch-migrate never kills a mutation itself.

The exact rules, starting with how `up` recognises a mutation it started on an earlier run, are
settled in a short design note before the 0.7 plan (see Open questions).

**Accept:** integration tests show that a migration whose mutation fails exits non-zero with the
failure reason and leaves the version table unchanged; and that killing `up` while a mutation
runs, then running `up` again, waits on the same mutation without creating a second one.

### 6. `ch-migrate plan <env>`

For each pending migration, before anything runs:

- every statement classified as **metadata-only**, **mutation** (rewrites parts), or
  **rebuild required** (cannot be done in place);
- for mutations, the data that will be rewritten, from `system.parts_columns`: exact where it is
  knowable (a column type change rewrites that column in every part), otherwise a ceiling
  labelled as one (an `UPDATE` rewrites at most the parts it could touch). `plan` never presents
  an estimate as an exact figure;
- for statements that need a rebuild, whether the target engine collapses `rebuild_table`'s
  possible duplicates (capability 8);
- downstream materialized views and dictionaries affected (from the existing `deps` graph);
- every `lint` finding.

`plan` replaces the current `large_table_mutation` rule, which compares a count of parts against
a row threshold and therefore never fires.

**Accept:** against a seeded test database, `plan` classifies a fixed corpus of statements
correctly, reports a column type change's rewrite size exactly as `system.parts_columns` gives
it, labels an `UPDATE`'s size as a ceiling, and emits the same result as `--json`.

### 7. CI-ready drift detection and machine-readable output

- `status`, `history`, `plan`, `lint` and `diff` accept `--json`.
- From 1.0 the `--json` output is a public interface. Each document carries a `schema_version`,
  and a breaking change to it requires a major version.
- `diff` (already present) is documented as a CI gate, with a working GitHub Actions example.

**Accept:** each command's `--json` output validates against a published schema; the example
workflow fails a build when the live schema drifts from the snapshot at head.

### 8. `op.rebuild_table()`

A first-class operation for changes that cannot be made in place, such as a new sorting key,
primary key or engine. Writers keep running throughout. The mechanism and its evidence are in the
[rebuild spike](2026-10-02-rebuild-spike.md).

**The guarantee: no acknowledged row is lost, and a small number may be duplicated.**
- **Duplicates:** rows committed or flushed between the copying view's creation and the
  snapshot's completion (server time) can land twice. On a `ReplacingMergeTree` target they
  collapse on merge, and `plan` says up front which case applies.
- **The one exception: unacknowledged async inserts.** Rows written with `async_insert = 1` and
  `wait_for_async_insert = 0` that are still in ClickHouse's queue at the instant of the swap are
  dropped by ClickHouse. Their writers were never told whether the write succeeded, which is
  ClickHouse's fire-and-forget contract.
  - Before it starts, `rebuild_table` looks for such writers. It requires an opt-in written in the
    migration file before it will proceed.
  - After the swap, it reports any entries ClickHouse rejected.
- **Writers that wait for acknowledgement** (the default) may see a transient error at the swap,
  and should retry.
- **Out of scope for 1.0:** exactly-once rebuilds with writers running, because they need merges
  stopped on the live table for the whole copy.

The steps. Each is checked before it runs, so the operation is safe to re-run (capability 4), and
a per-table lock prevents two runs at once:

1. Create the replacement table, and a materialized view that copies new inserts from the old
   table into it.
2. Wait for inserts and async-insert flushes that began before the view existed to finish, so
   none is missed.
3. Snapshot the old table with `ATTACH PARTITION FROM`, which links files rather than copying
   data.
4. Copy the snapshot into the replacement one partition at a time, through a staging table. A
   re-run resumes at the first unfinished partition, first stopping any copy still running from
   the interrupted run.
5. Flush the async-insert queue, swap with `EXCHANGE TABLES`, then drop the copying view.
   Dropping it waits for inserts already in flight, so it acts as a barrier. Materialized views
   follow the table name across the swap, so dependent views need no re-pointing.

**Supported:** a single server, ClickHouse Cloud, and replicated tables. Refused with a clear
message, before anything is created:
- a sharded table (a `Distributed` table over per-shard tables), because the swap cannot be
  atomic across shards;
- a change to the partition key, because a partition copy could no longer be resumed cleanly;
- a table with unfinished mutations, because mutations made after the snapshot would not carry
  over.

**Accept:** an integration test inserts continuously during a rebuild that changes the sorting
key; after the swap, every acknowledged row is present and every duplicate was committed inside
the documented window; stopping the rebuild partway and running `up` again resumes from the last
copied partition and completes.

## What 1.0 is not

- **Not a dialect.** DDL compilation and autogenerate belong to clickhouse-connect.
- **Not declarative.** Migrations stay imperative revisions, written in SQL.
- **Not a data pipeline.** Moving data between systems is out of scope; `rebuild_table` moves
  data only within one table's rebuild.
- **Not a hosted service.** ch-migrate is a CLI and a library.
- **Not exactly-once, sharded or partition-key rebuilds.** All may come later. In 1.0,
  `rebuild_table` promises no acknowledged row is lost rather than no duplicates. It refuses
  sharded tables and changes to the partition key.

## Compatibility

- Existing users who pin a git commit are unaffected until they choose to move.
- 0.x projects upgrade with `ch-migrate upgrade-env`; existing Python migration files keep
  working and do not need converting to SQL.
- The idempotency gate applies only to migrations written after the upgrade. `upgrade-env`
  records the current head as a baseline in the committed project config, and revisions at or
  before the baseline are exempt in every environment. A migration already applied in dev but
  still pending in prod is therefore not blocked by the upgrade.
- **Python:** 0.5 is the last release that supports Python 3.9. From 0.6, ch-migrate requires
  Python 3.10 or later, because the official dialect's Alembic integration requires it, and so
  does Alembic itself since 1.17. On 3.9, pip keeps resolving to 0.5.x. `uv tool install`
  provides its own interpreter.
- **ClickHouse Cloud:** each version's acceptance check runs the integration suite against a
  ClickHouse Cloud service on DRY's own account, as well as against local self-hosted
  containers.

## Releases

Implementation runs straight through to 1.0. Each capability is tested locally against a real
ClickHouse server before the next begins. Publishing is a separate decision: versions are tagged
and posts published on whatever cadence suits the series. Each version's work is broken into
tickets with their own acceptance and validation steps, and each version ends with an acceptance
check that maps every check below to a passing test. Spike findings and design notes are
committed under `docs/design/`.

| Version | Delivers |
|---|---|
| 0.4.1 | Capability 1, shipped early to claim the PyPI name: `clickhouse-alembic`, single-source version, public CI, tag-triggered release |
| 0.5 | Capability 2 (SQL-first `new`, irreversible migrations), README covering every command |
| 0.6 | Capabilities 3 and 4 (official dialect, session-safe connections, version table that can't re-run a migration, `SET` lint, idempotency gate); Python 3.10+ |

| 0.8 | Capabilities 6 and 7 (`plan`, `--json`, CI drift gate) |
| 1.0 | Capability 8 (`rebuild_table`) |

## Open questions

Each group is settled before the plan for its release is written, not assumed.

**A spike on the official dialect, before the 0.6 plan.** Answered in the
[dialect spike](2026-10-02-dialect-spike.md): yes, the dialect holds a session; its version table
fails closed when interrupted, but nothing replicates the table on self-hosted clusters; bootstrap
is unaffected; Python 3.9 is not supported, so 0.6 requires 3.10.

1. Does the clickhouse-connect synchronous dialect hold one ClickHouse session per connection,
   so that a `SET` persists across statements within a migration?
2. What engine does it create `alembic_version` with, and does that behave correctly on
   ClickHouse Cloud and on a replicated self-hosted cluster?
3. Does `bootstrap` (roles, users, grants) sit cleanly on the new connection path?
4. Does the dialect support Python 3.9? If not, it is ruled out for 1.0 (see Compatibility).

**A design note on waiting, before the 0.7 plan.** Experiments and proposed rules:
[waiting design](2026-10-02-waiting.md). Accepted-but-unacknowledged mutation recovery
is demonstrated; the missing/expired-evidence case needs a decision before implementation.
The note does not weaken capabilities 4 or 5 without that decision.

5. On a re-run, how does `up` recognise a mutation it started earlier, without mistaking someone
   else's mutation for its own?
6. What does `up` do when the table already has unfinished mutations it did not start? Mutations
   on one table run in order, so its own will queue behind them.
7. On replicated tables, how does `up` confirm that every replica has finished, not only the one
   it is connected to?
8. For `ON CLUSTER` DDL, what counts as finished when a host is down?
9. How much of capability 5 applies on ClickHouse Cloud, where `ON CLUSTER` is unnecessary?

**A spike on rebuilds, before the `rebuild_table` plan.** Answered in the
[rebuild spike](2026-10-02-rebuild-spike.md): views follow the name; `ATTACH PARTITION FROM`
works between replicated tables. ClickHouse Cloud is unverified and is checked on the DRY Cloud
service.

10. Across `EXCHANGE TABLES`, does a materialized view follow the table name or the table itself?
    The answer decides the order of step 5.
11. Does `ATTACH PARTITION FROM` work on ClickHouse Cloud and between replicated tables?
